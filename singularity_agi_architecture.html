2. 'Smart Rotation' Logic

To bypass the constraints of free-tier Rate Limits (RPM/TPM), the system implements a "Virtual Global Provider" layer. This layer manages a pool of API keys and dynamically routes requests based on real-time telemetry.

[Request Dispatcher] | |---> [Health Monitor] <--- (Telemetry: Rate Limits, Latency, Errors) | |---> [Smart Router] | |--- Pool A: Groq (High Speed, Low TPM) |--- Pool B: OpenRouter (High Logic, Variable Latency) |--- Pool C: Gemini (High Context, Medium RPM)

Pseudo-code: SmartRotation Engine

class SmartRotationManager {
  private pools = {
    "groq": { keys: [...], rpm: 30, currentUsage: 0 },
    "openrouter": { keys: [...], tpm: 100000, currentUsage: 0 },
    "gemini": { keys: [...], rpm: 15, currentUsage: 0 }
  };

  async executeTask(taskType, payload) {
    const provider = this.selectBestProvider(taskType);
    try {
      const response = await provider.call(payload);
      this.updateTelemetry(provider.id, response.headers);
      return response;
    } catch (err) {
      if (err.status === 429) {
        this.markProviderCoolDown(provider.id);
        return this.executeTask(taskType, payload); // Recursive retry on next best
      }
    }
  }

  selectBestProvider(taskType) {
    // Logic: If 'refactor' -> Groq; If 'architecture' -> OpenRouter; 
    // If 'whole-repo-scan' -> Gemini
    return this.getAvailableProviderFromPool(taskType);
  }
}

The logic tracks X-RateLimit-Remaining headers to proactively switch keys before a 429 error occurs, ensuring a continuous development flow.

3. Full-Stack Orchestration Workflow

The system follows a non-linear, agentic workflow where "The Architect" oversees specialized sub-agents.

  1. Requirements Phase: Gemini 2.0 processes natural language input, generates a PRD (Product Requirements Document), and creates a structural "Tree Map" of the desired application.
  2. Planning Phase: OpenRouter (Llama 4) designs the Supabase schema, API endpoints, and component hierarchy. It outputs a system_blueprint.json.
  3. Code Generation Phase:
    • Backend: Groq generates Supabase Edge Functions and SQL migrations.
    • Frontend: Groq/OpenRouter parallel-process React/Next.js components based on the blueprint.
  4. Validation Phase: A dedicated "Reviewer" agent runs the code through a virtualized linter. If errors are found, the 'Smart Rotation' logic picks a different model to attempt a fix, preventing "Model Hallucination Loops."

4. Automated Deployment Strategy

The Singularity Builder manages the entire lifecycle from local generation to global distribution using CLI automation and GitHub Actions.

CI/CD Pipeline Architecture:

# .github/workflows/singularity-deploy.yml
name: Autonomous Deployment
on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Supabase
        run: npx supabase login --token ${{ secrets.SUPABASE_ACCESS_TOKEN }}
        
      - name: Deploy Database & Edge Functions
        run: npx supabase db push && npx supabase functions deploy

      - name: Deploy Frontend to Netlify
        uses: netlify/actions/cli@master
        with:
          args: deploy --build --prod
        env:
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}

The builder dynamically injects these configuration files into the generated repository. It uses the Netlify CLI for atomic deployments, ensuring that if a build fails, the previous version remains live.

5. Security and Secret Management

Handling multiple free-tier API keys requires a robust security posture to prevent leaks and unauthorized usage.

The "Vault-and-Proxy" Pattern:

  • Secret Injection: API keys are never stored in code. They are injected into the Builder via environment variables (.env.local) and synced to GitHub Actions Secrets using the GitHub CLI (gh secret set).
  • Encrypted Key Rotation: If the builder is hosted, it uses AES-256-GCM to encrypt keys at rest within the Supabase Vault.
  • Scoped Access: The builder creates "Limited Service Roles" in Supabase. This ensures that the generated app only has access to its own data, while the Builder's administrative keys remain isolated.
  • Rate Limiting (Self-Imposed): To prevent being flagged for "API Farming," the builder implements jitter (randomized delays) between requests, mimicking human development patterns.

Secret Management Workflow:

1. Developer provides keys (OpenRouter, Groq, etc.) via a secure UI.
2. Builder encrypts keys and stores them in Supabase Vault.
3. During Orchestration, the 'Smart Rotation' engine decodes keys in-memory.
4. For the generated app, the Builder generates a unique 'SUPABASE_ANON_KEY' 
   and 'NEXT_PUBLIC_...' variables for Netlify.
